# FacetRT / FacetEB 硬件光线查询可见性后端

2026-11-26。本文说明可见性图的第二个后端：用 `VK_KHR_ray_query` 在面元三角形的 BLAS/TLAS 上逐像素枚举全部交点，替代 A-buffer 光栅。原光栅后端保留为默认和回退。

## 开关

| 环境变量 | 取值 | 说明 |
|---|---|---|
| `HISTREAM_FACET_VISIBILITY` | `auto`（缺省）、`raster`、`rayquery` | 覆盖工程字段 `control.facetVisibility`（同样的取值，缺省 `auto`）。`auto`：设备支持光线查询则用，否则静默用光栅；`rayquery`：同上但不支持时打印警告；`raster`：原光栅路径；其他值报错。测试用 `HISTREAM_FACET_FORCE_NO_RAYQUERY=1` 模拟不支持光线查询的设备 |
| `HISTREAM_FACET_VALIDATE_VISIBILITY` | `1` | 同一次运行里两个后端各建一次图并打印差异（见下），主后端的结果继续使用；也比较太阳可见比例 |
| `HISTREAM_FACET_DUMP_GRAPH` | 文件路径 | 开发诊断：把可见性图（分母、天空、地面计数与 CSR 边）写成二进制，GPU 与 CPU 后端均支持，格式见 `facetrt_vulkan.h` 的 `dumpGraph` |
| `HISTREAM_FACET_GRAPH_BUILD` | `gpu`（缺省）、`cpu` | 哈希表 → CSR 在 GPU 上构造（`graph_build.comp`）或在 CPU 上构造（原路径）；其他值报错。GPU 路径失败（缺少着色器、超出 `maxStorageBufferRange`/显存、行度数过大等）时打印原因并回退 CPU |
| `HISTREAM_FACET_VALIDATE_GRAPH` | `1` | 同一次运行里 GPU 与 CPU 各构造一份 CSR，逐位比较（行偏移、全部边、每行边计数和），打印 `IDENTICAL` / `MISMATCH`；不一致时使用 CPU 的结果 |

实际使用的后端写入日志（`facetrt: visibility backend ray-query (...)`）、`facetrt.json` 与 `faceteb_run.json` 的 `execution.visibility`（`raster` / `ray-query` / `cpu-raster`）。

设备要求：Vulkan 1.2，`VK_KHR_acceleration_structure`、`VK_KHR_ray_query`、`VK_KHR_deferred_host_operations`，特性 `accelerationStructure`、`rayQuery`、`bufferDeviceAddress`。扩展只在请求了光线查询后端且设备支持时启用，默认路径的设备创建不变。着色器 `visibility_rayquery.comp.spv`、`direct_rayquery.comp.spv` 缺失时同样回退。

## 做法

- **BLAS**：`m_vertices` 的非索引三角形列表，每面元一个图元（`gl_PrimitiveID` = 面元号）；几何不设 opaque，并带 `NO_DUPLICATE_ANY_HIT`，所以 `rayQueryProceed` 对每个候选三角形各返回一次，着色器从不 Confirm，得到沿线**全部**交点。地面面元与其他面元一样在 BLAS 中。
- **TLAS**：实例 0 为中心瓦片，实例 1..N 为周期副本（平移 `tile × periodicSize`，顺序与光栅路径的 `periodicTileOffset` 相同），`instanceCustomIndex` 为瓦片序号，非 0 即副本（副本只遮挡/发射，不作接收面）；关闭背面剔除。加速结构约 7 MiB，构建 20–70 ms。
- **射线**：由每个方向原有的 `viewProjection` 求逆得到：深度 0 起点、深度 1 终点，像素中心采样；命中深度 = t/射线长，与光栅深度同一标度。太阳方向的 4×4 亚像素抖动通过矩阵平移项原样沿用。
- **`visibility_rayquery.comp`**：每线程一个像素，枚举交点 → 排序 → 去重 → 之后与 `visibility_resolve.comp` 逐行相同（分母、天空、地面、相邻片元边、同一个哈希表与 `addEdge`）。写入的缓冲与光栅路径完全相同，所以回读、CSR、下边界、求解、能量、光谱都不改。`direct_rayquery.comp` 同理对应 `direct_resolve.comp`。公共部分在 `visibility_rayquery.glsl`，`shader\facetrt` 与 `shader\faceteb` 两份保持一致。
- 不再分配 A-buffer（占位 1 个元素）。

## 与光栅路径的差异（诚实说明）

1. **统计等价，不是逐位一致。** 两者都是“像素中心 × 同一组方向”的采样，但像素是否覆盖三角形的判定（光栅为左上填充规则，光线查询为水密求交）与深度的舍入不同，约 1% 的相邻边计数会差几个样本。默认光栅路径与改动前的引擎逐位一致（已核对 `facetrt.json`）。
2. **排序键与光栅相同**：（深度，侧编号），副本位使同深度时中心片元在前。光线查询的深度带舍入误差，故深度差 ≤ 1e-6（深度已归一到 [0,1]）按并列处理，由侧编号定序。共面重叠的面元（如同一高度重叠的屋顶面）其先后本来就由舍入噪声决定，两个后端会在这类面元上有不同取舍（见验证）。
3. **共享边/顶点的重复命中**：光栅每个像素对共享边只落一个三角形，光线查询可能两个都报。去重规则：同一侧（含副本位）且深度差 ≤ 1e-6 → 视为重复丢弃；两条命中的重心坐标都在边上（≤ 1e-4）且深度差 ≤ 1e-6 → 只保留（深度，侧编号）较小者。
4. **每条射线最多 256 个交点**（与光栅路径着色器上限相同）。超出时抛 `RayQueryOverflow`，自动重建为光栅后端继续（已用 6 个交点上限的测试着色器验证建图与太阳可见比例两条回退路径）。
5. 小于一个像素的面元仍可能零样本，这是栅格采样本身的限制，光线查询不改变它（要提高精度只能提高栅格边长，见下）。

## GPU 图构建（哈希表 → CSR）

2026-11-26。两个可见性后端原先都把整张边哈希表（作物约 33 M 槽，森林上限 4 GiB 键 + 2 GiB 计数）回读到主机，再逐槽取边、排序、建 CSR：作物约 2 s，森林约 17 s，是图构建时间的主体。现在由 `graph_build.comp` 在设备上完成，`radiosity` / `incident` 直接使用设备端 CSR。

阶段（每阶段一次调度，网格步进循环，调度间有屏障）：统计非空槽 → 每个槽写出两个有向条目并累计行度数 → 对行偏移做三段式前缀和 → 按行偏移散布 → **行内排序**（每个条目数出同一行里邻居编号更小的条目数作为名次，行内邻居编号唯一故名次唯一）→ 每行边计数和。结果与 CPU 路径（按键排序的对称 CSR，每行邻居升序）**逐位相同**，不依赖线程调度。

- 主机只回读：每侧分母/天空/地面计数（`applyGroundBoundary` 仍在 CPU 上做）、4 个控制字、每行边计数和（CPU 用同样的浮点运算算闭合误差，因此 `closureError` 与原来逐位相同）。CSR 留在设备上；需要主机副本时（无 `shaderFloat64` 的设备做 CPU 入射辐照度、`HISTREAM_FACET_DUMP_GRAPH`）才回读。
- 行内 O(d²) 排序的代价由度数平方和控制：超过 2×10¹¹ 则回退 CPU（作物、城市、森林均远低于此）。
- 额外显存只在构图期间占用（每个有向边约 28 B），其中 CSR 边表本身（8 B）保留给求解。
- 回退：缺少 `graph_build.comp.spv`、扫描块数 > 65535（> 6.7 千万侧）、单缓冲超出 `maxStorageBufferRange`、分配失败等，都会打印 `GPU graph build unavailable (...)` 并走 CPU 路径（哈希表保持原样）。

**验证**（`HISTREAM_FACET_VALIDATE_GRAPH=1`，同一次运行 GPU CSR 与 CPU CSR 逐位比较）：`frt_crop`、`frt_crop_periodic`、`frt_urban_mwir` 在光栅与光线查询两个后端下全部 `IDENTICAL`；森林（31.7 M 侧、10.3 M 有向边）光栅后端 `IDENTICAL`。最终结果：以上各场景的光栅、光线查询两个后端，`facetrt.json` 的 `sunlit`、`radiosity`、`bandRadiosity`、`bandStates`、`lightEnhancement` 与 `graph` 与改动前的引擎逐位相同（森林同样；FacetEB `feb_crop` 的 `sunlit`、辐射度、温度、净辐射、潜热逐位相同）。`HISTREAM_FACET_GRAPH_BUILD=cpu` 与缺少着色器时的回退结果同样逐位相同。

**耗时**（图总耗时 = `facetrt.json` 的 `timing.visibilityMs`，1024²，40 方向）：

| 场景 | 光栅 改动前 → 后 | 光线查询 改动前 → 后 |
|---|---|---|
| frt_crop | 5.2 s → 1.4 s（后者含 64→128 层溢出重建） | 3.1 s → 0.14 s |
| frt_urban_mwir | 3.5 s → 0.29 s | 2.1 s → 0.06 s |
| forest（15.8 M 面元） | 18.6 s → 3.2 s | 20.5 s → 3.2 s |

哈希表 → CSR 本身：作物/城市约 25 ms（原约 2 s），森林 1.2 s（原约 17 s）。森林剩下的 3 s 主要是每侧三个计数数组（共约 380 MB）的回读（1.7 s）和 GPU 行内排序（1.2 s）。整次运行的墙钟时间：作物 FacetRT 6–8 s → 约 3–4 s；森林主要被谱段求解占据（约 100–140 s），变化不明显（机器上另有负载，波动约 ±30%）。

面元数（1580 万）已超过 4096² 的像素数（1670 万），4096² 仍有 28.6% 的接收侧没有样本（被当作完全开阔天空），所以**这里的 4096² 参考本身不收敛**，上面的偏差只是下限；1024² 的“+30% 物体侧偏差”主要是无样本面元被当成天空造成的系统偏高。要真正解决需要按面元采样（每个面元自己发射半球射线，见“建议”），仅靠提高栅格边长不够。边数随分辨率增长很快（1024²：10.3 M，2048²：36 M，4096²：117 M 有向边），4096² 的求解阶段明显变慢。

### 建议（未改动缺省）

1. **后端缺省**：已于 2026-11-26 改为 `auto`（见上节）。等价性已验证（见上文），省去 A-buffer（作物 1–2 GiB）与溢出重建，图构建在 GPU 图构建加持下比光栅快 2–10×；不支持光线查询的设备自动回退光栅。
2. **分辨率**：建议按面元数自适应，使每个面元平均有足够多的像素：`size = clamp(nextPow2(sqrt(64 × 面元数)), 1024, 4096)`（作物 141 k 面元 → 4096；城市 → 4096；面元少的场景保持 1024）。作物 4096² 比 1024² 整次运行只多约 0.8 s（FacetRT 1.4 → 2.2 s，FacetEB 6.1 → 7.1 s），逐面元误差降到 1/4 左右、FacetEB 面元温度平均误差 0.23 K → 约 0.05 K（外推）。城市无收益但也不贵。对 1580 万面元的森林，4096² 的整次运行增加约 25%（104 s → 130 s）、边表 117 M，且仍有 28.6% 无样本侧，收益有限且偏差方向（偏高）不变。
3. **森林/稠密亚像素场景**：优先考虑按面元采样的半球射线（余弦加权，光线查询可直接做），它对每个面元都有样本，不依赖栅格分辨率；在此之前日志里的 `no visibility sample` 行（无样本接收侧数及比例）可作为风险提示：超过约 5% 时建议提高 `HISTREAM_FACET_RASTER_SIZE`（对作物 1024² 为 2.6%，城市 0.05%，森林 82%）。
4. 暂不建议把 4096² 设为全局缺省：森林上边数与求解时间显著增加，且 `HISTREAM_FACET_RASTER_SIZE` 对现有 `kRasterSize` 的自适应（大场景 2048²/16 层）仍按光栅路径的显存预算设计，改缺省需要同时调整。

## 缺省后端 auto（2026-11-26）

`control.facetVisibility`（`auto` | `raster` | `rayquery`，缺省 `auto`）在 `facetInputView` 里转成 `<facetVisibility>`，由 `FacetrtVulkan::initialize` 读取；环境变量 `HISTREAM_FACET_VISIBILITY` 覆盖。非法值报 `control.facetVisibility must be auto, raster or rayquery`。（Facet 模式不经过 `fileio_json.cpp`，该文件只服务其他模式。）不支持光线查询的设备（或缺少 `visibility_rayquery.comp.spv`）静默回退光栅，结果与显式 `raster` 逐位相同（用 `HISTREAM_FACET_FORCE_NO_RAYQUERY=1` 验证）。

**auto 对 raster（类别面积加权均值差）：**

| 算例 | 项目 | 差 |
|---|---|---|
| frt_crop / frt_crop_periodic / frt_urban_mwir | 受光比例、各波段辐射度 | 受光比例 ≤ 5×10⁻⁵；波段辐射度类别均值相对差 ≤ 0.003% |
| feb_crop（2 节点） | 物体侧温度 | +0.0001 K（地面 +0.00004 K） |
| feb_crop | 净辐射 / 潜热 / 显热 / 储热 | +0.002 / −0.0002 / +0.0006 / +0.0001 W/m²（地面 ≤ 0.0008） |

整次运行墙钟：frt_crop 5.1 → 3.0 s，frt_crop_periodic 4.0 → 3.0 s，feb_crop 17.1 → 8.1 s（光栅为含 A-buffer 溢出重建的时间）。结果 JSON 顶层 `quality` 与 `faceteb_run.json` 的 `quality` 给出实际后端和 `zeroVisibilitySamples`（无可见性样本的接收侧占比，见下节“分辨率”），供服务端告警。

**深度并列容差随场景尺度收紧。** 光线查询着色器把深度差 ≤ 容差的命中视为并列（按侧编号定序）或重复命中；深度已归一到 [0,1]，容差 1e-6 对应几何距离 1e-6×2r。外接球很大时这会接近厚 1 cm 的地面，故现在由主机经推送常量 `periodic.w` 给出 `clamp(5 mm / (2r), 1.5e-7, 1e-6)`（`FacetrtVulkan::rayTieDepth`）：2r < 5 km 的场景保持 1e-6（结果不变），更大的场景收紧到不超过约 5 mm。验证（把 `frt_crop` 的域和 144 株植物按 ×500、×1000 放大成 10 km、20 km 域，500 m 高的植株，地面 y = −0.01，2048²，对 CPU 光栅）：边 Σ|Δ|/Σ 0.11%（固定 1e-6 时 0.20%），天空差最大 1.5%，没有差 > 2% 的侧。所有可见性方向都从上方看，物体与其下的薄地面的先后同时受侧编号并列规则保护（物体侧编号小于地面）。这类大场景用 A-buffer 光栅会溢出（16 层、4 GiB 上限），光线查询可以运行。

## 耗时分解与森林剖面（2026-11-26）

`facetrt.json` 的 `timing` 现在给出分阶段耗时（ms）：`totalMs`（引擎运行，与原含义相同）、`wallMs`（整次：setup + 引擎 + 写出）、`setupMs`（读工程/OBJ + 实例展开，`setupStages` 再分 `objReadMs`、`instanceExpandMs`、`groundMs`、`finalizeMs`）、`gpuInitMs`（设备 + 几何上传 + 加速结构）、`visibilityMs`（`visibilityStages`：`accelerationBuildMs`、`passesMs`、`countReadbackMs`、`csrBuildMs`、`finalizeMs`）、`sunlightMs`、`opticsPrepMs`、`solveMs`（`bandSolves`：每波段 `iterations`、`ms`、`warmStart`；`diffuseBaselineMs`）、`outputReadMs`（光谱输出回读）、`outputWriteMs`（序列化 + 磁盘）。`faceteb_run.json` 的 `timing` 有对应字段：`setupMs`/`setupStages`、`gpuInitMs`、`visibilityMs`/`visibilityStages`、`sunlightMs`（全部节点）、`radiationMs`（全部辐射求解与入射评估）、逐节点 `nodes[]`（短波窗口 / RT-EB 耦合 / 节点输出）、`finalOutputWriteMs`、`wallMs`。`outputWriteMs`、`wallMs` 在文件写完后原位回填（数字前有空白，仍是合法 JSON）。

**森林（15.8 M 面元，JSON 输出 9.0 GB），改动前的整次 118 s 的构成：**

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 写出 JSON（序列化 + 磁盘） | 85.2 s | 72% |
| setup（OBJ 读 0.7 s + 实例展开 13.3 s） | 13.2 s | 11% |
| 光谱输出回读（2.4 GB，**从未缓存的主机内存读，约 0.2 GB/s**） | 12.3 s | 10% |
| 可见性图 | 3.3 s | 3% |
| 太阳可见比例 | 1.6 s | 1.4% |
| 6 个波段求解（各 64 次迭代，76 ms/波段）+ 漫射基线 | 0.5 s | 0.4% |
| optics 准备 0.65 s、GPU 初始化 0.77 s | 1.4 s | 1.2% |

结论：**GPU 求解不是瓶颈**（0.5 s），瓶颈是写 JSON、实例展开和回读。针对这三项：

1. **回读用 host-cached 内存**：`downloadBuffer` 的 staging 缓冲此前取第一个 host-visible + coherent 类型（非缓存，读取 ≈ 0.2 GB/s）；现优先 `HOST_VISIBLE | HOST_COHERENT | HOST_CACHED`，没有则非 coherent 缓存类型并 invalidate，再没有才退回原类型。光谱输出回读 12.3 s → 0.6 s，每侧计数回读 1.75 s → 0.08 s，可见性图 3.3 s → 0.5 s，太阳可见比例 1.6 s → 0.4 s。对所有回读生效，结果不变。
2. **实例展开快速路径**（结果逐位相同）：完全位于域内的三角形（与 `clipPolygonToPlane` 同样的 1e-6 容差）不再经过 6 次多边形裁剪的堆分配；材质匹配不再复制组名字符串；顶点/材质数组按 1.5 倍预留。展开 13.3 s → 3.3 s（`setup` 14.2 → 4.2 s）。
3. **二进制输出**（`control.facetOutputFormat = binary`，见 `docs/facet-binary-output.md`）：写出 76–85 s → 2.7 s（3.0 GB；磁盘冷写时曾测到 26 s，本机持续写盘约 280 MB/s，页缓存状态影响很大）。顶点位置分块追加，不再复制整个数组。

**森林改动后：** 二进制输出整次 **12.1 s**（setup 4.2、gpuInit 0.8、可见性 0.46、太阳 0.4、optics 0.75、求解 2.3 含回读 0.66、写出 2.7）；JSON 输出整次 85.8 s（写出 76 s，其余同上）。作物/城市 JSON 输出的数值与改动前逐位相同（光栅与光线查询两个后端），FacetEB `feb_crop` 的 `faceteb.json` 数组同样逐位相同。

**`radiationSolver = "accelerated"` 没有把多个波段合并成一次读图**：`runGpuSpectral` 对每个波段单独调用 `solveSpectralBand`，每个波段的每次迭代各读一遍 CSR；“加速”的含义是 (a) 相邻同类（都是光学或都是热红外）波段用前一波段的物理解作初值（`warmStart`），(b) 每 8 次迭代检查收敛（间接调度）后提前停止，传统模式固定 64 次。作物示例 6 个波段的迭代数：传统 64×6 = 384；加速 8、8、8、16、24、8 = 72（第一个光学波段与热红外波段无热启动）；城市 2 个波段 8 + 8（传统 64 + 64，单波段 292 → 42 ms）。真正按多波段批量（同一次读图更新若干波段）尚未实现。

**可见性图后续优化（把 `applyGroundBoundary` / 每侧计数回读搬到 GPU、行内排序换分段基数排序）暂不需要**：剖面显示改动后森林可见性图只占 0.46 s（整次 12 s 的 4%），其中 CSR 构建 0.125 s（GPU 行内排序 59 ms）。当可见性图重新成为瓶颈（如更多方向、更大面元数）再做。

## 建议与限制

- 缺省已改为 `auto`（见下文“缺省后端”）；需要旧行为时设 `control.facetVisibility = "raster"` 或 `HISTREAM_FACET_VISIBILITY=raster`。精度只能靠提高栅格边长提升时，配合 `HISTREAM_FACET_RASTER_SIZE=2048/4096`。
- 光线查询路径中曾占时间大头的哈希表整表回读与取边已由 GPU 图构建取代（见上）；剩余的主机侧开销是每侧三个计数数组的回读和 `applyGroundBoundary`。
- 深度并列容差 1e-6 是相对整个深度范围的；场景外接球半径极大（数十公里）时对应的几何距离可达厘米级，可能与厚度为 1 cm 的地面（y = −0.01）混淆。
- 每像素 256 个交点的上限同光栅路径；超限时回退光栅，光栅再按其规则扩层。
